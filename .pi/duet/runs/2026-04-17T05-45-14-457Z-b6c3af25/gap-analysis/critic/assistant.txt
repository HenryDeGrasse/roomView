Blocking issues:
- The canonical scene model is not complete enough to support the required behaviors. It references undefined core types (`ConstraintSpec`, `FixedElement`, `Polygon2D`, `RectOnSurface`, `Pose3D`, `OBB3D`) and later relies on concepts that are not represented in the model at all (`north wall`, `focal element`). It also lacks the relationship/support data needed for anchored/fixed-object validation and underspecifies parent/child semantics despite `parent_id`, `include_children`, and `PARENT_MOVE_VIOLATION`. This needs one coherent schema pass before implementation.
- The versioning/mutation boundary is internally inconsistent. `Scene` includes `assets`, `photoreal_gallery`, and `derived_state`, but the doc says `scene_version` only increments for committed edit plans, while splat attachments and gallery additions also mutate scene state. The PRD needs to define what is actually versioned vs sidecar metadata, how undo works (restore old snapshot vs create a new head pointing to prior state), and how stale-tab/conflict behavior applies across those mutations.
- The command/API contract needs one consistent authority model. Right now `generate_photoreal` and `undo_last_change` are both typed operations and separate dedicated endpoints, and `/plan` → `/apply` does not specify whether the client may alter the previewed plan, how the server prevents tampering, or how idempotency/conflicts are handled at apply time. The PRD should explicitly separate scene-edit operations from command endpoints and define a server-authoritative apply contract.
- The primary cross-device handoff/privacy model is undefined. The main flow is “scan on iPhone, then open the scene on a laptop with `scene_id`,” while privacy says no public sharing. The PRD needs an explicit access model for that handoff (auth, QR/magic link, one-time token, paired session, or an explicit decision to rely on opaque unguessable scene URLs). As written, the core user flow is not safely specified.
